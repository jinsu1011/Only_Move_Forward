# 발표 대본 — 9반 P286 김진수 · 전진만할게요

> 발표 자료는 제출한 개요 PDF 25쪽 그대로. 별도 자료 없음.
> 채점: 전달 능력 6점(문제 → 기능 → 설계 순서로 이어지는가 · 설계 상의 고민과 다음 단계를 말하는가) + 시간 엄수 4점(**4분 30초 ~ 5분**, 초과·2분 미만 감점).
> 분량 약 1,590음절. 보통 속도(340음절/분)면 **4분 40초**, 빠르면 4분 25초, 느리면 4분 58초.
> → 리허설에서 4분 40초 근처로 나오면 그대로 가고, 5분에 닿으면 아래 "버리는 순서"를 쓴다.

## 0:00 — 1쪽 표지

안녕하세요. 9반 P286 김진수입니다.
제가 만든 **전진만할게요**는 운전면허 준비자를 위한 학습 보조 웹 서비스입니다.

> 표지에서 머물지 않는다. 2쪽 목차는 **건너뛴다**.

## 0:10 — 3쪽 서비스 개요

1종·2종 보통 면허를 준비하는 사람이 대상이고, 필기 오답과 주행 연습 기록을 한곳에 모아 다음에 뭘 연습할지 정해 줍니다.
왜 만들었는지부터 말씀드리겠습니다.

## 0:22 — 4쪽 문제 정의 〔문제〕

지금은 필기는 문제 풀이 앱으로, 주행은 학원 실차 교육으로 따로 준비해서 두 기록이 연결되지 않습니다.
그래서 문제가 셋입니다.
왜 틀렸는지 모른 채 같은 주제를 반복해서 틀립니다. 앱이 정답만 주고 근거 조문은 안 보여 주니까요.
신호위반이나 보호구역 속도처럼 **한 번에 불합격이 되는 항목이 열한 개**인데, 실차 연습은 시간과 비용 때문에 이걸 미리 겪어 볼 기회가 없습니다.
그리고 필기 약점과 주행 실수를 함께 놓고 다음 연습을 정할 방법이 없습니다.
왼쪽 수치는 별표26과 도로교통공단 시험 안내에서 가져왔고 조회일을 아래 적어 뒀습니다.

## 0:57 — 5쪽 핵심 가치 〔기능〕

이 세 문제에 기능을 하나씩 붙였습니다.
오답은 제출한 뒤에만 정답을 공개하고, 검수 해설과 조문 근거를 같이 보여 줍니다.
주행은 도심 A코스에서 신호·어린이보호구역·횡단보도를 지나며 별표26 항목에 연결된 판정을 받습니다.
그리고 이 둘을 묶어 AI 통합 리포트가 다음 연습을 정해 줍니다.

## 1:17 — 6쪽 범위

범위는 의도적으로 좁혔습니다.
학습자 한 명이 혼자 쓰는 흐름만 넣었고, 공식 문제은행과 모의고사는 **이용 조건과 정답 검수가 끝나지 않아 껐습니다.** 뒤에서 한 번 더 말씀드리겠습니다.

## 1:30 — 7·8쪽 액터와 기능

액터는 사용자 둘, 외부 시스템 둘 — 학습자와 방문자, LLM 서비스와 센서 핸들입니다.
센서 핸들은 아두이노에 MPU-6050을 붙인 물리 핸들인데, 브라우저가 Web Serial로 직접 읽어서 **서버 API가 없습니다.**
8쪽은 기능 열여덟 개마다 화면과 API를 붙여 놓은 표이고, 이게 뒤 설계의 기준입니다.

## 1:52 — 9쪽 전체 UI 흐름 〔설계〕

화면은 열세 개입니다. 방문 → 필기 → 주행 → 리포트가 대시보드를 중심으로 이어지고, 세션이 만료되면 로그인으로 보냈다가 원래 화면으로 되돌립니다.
10쪽부터 18쪽이 화면별 상세인데, 설계 판단이 들어간 세 장만 보겠습니다.

## 2:10 — 12·14쪽 필기

필기는 보기를 누를 때마다 서버에 저장해서 새로고침해도 복원됩니다.
대신 **제출 전에는 정답을 응답에 아예 담지 않습니다.** 제출 전에 요청하면 409로 막습니다.
14쪽 AI 오답 코칭에서 제일 고민했습니다. 정답과 규칙은 검수 데이터가 정하고 AI는 설명만 하게 했습니다. 입력에 없는 조문을 인용하면 서버가 거부하고, 그때도 검수 해설은 그대로 남습니다.

## 2:35 — 16·17쪽 주행

주행은 실격에 해당하는 사건이 나도 **끊지 않습니다.** 사건을 쌓아 두고 끝까지 갑니다. 공식 시험이 아니라 연습이니까, 한 번 틀렸다고 끊으면 연습이 안 되기 때문입니다.
17쪽 결과 화면이 핵심입니다. 브라우저가 보낸 사건을 그대로 믿지 않습니다. 입력 기록을 서버가 같은 엔진으로 다시 재생해 사건을 확정하고, 다르면 "불일치, 서버 기준"으로 표시합니다.

## 3:00 — 19쪽 예외

19쪽은 예외 시나리오입니다. 입력 오류·세션 만료·저장 실패·센서 단절까지, **오류가 나도 입력과 기록은 보존하고 다음 행동을 안내하는 것**을 원칙으로 잡았습니다.

## 3:12 — 20~22쪽 데이터 모델

테이블 스무 개, 관계 스물일곱 개입니다. 신경 쓴 건 둘입니다.
**버전 보존** — 문항·코스·출처는 고칠 때 덮어쓰지 않고 새 버전을 추가합니다. 과거 결과가 그대로 남아야 하니까요.
**상태 무결성** — 제출했으면 점수가 반드시 있고, 센서 모드면 보정값이 반드시 있도록 제약을 걸었습니다.
22쪽은 화면 값이 어느 API 필드와 어느 컬럼에서 오는지 붙인 대응표입니다.

## 3:37 — 23·24쪽 API

API는 OpenAPI 3.0.3으로 24경로 27동작이고, 공통 스키마는 `$ref`로 재사용, 오류는 전부 같은 형식입니다.
하나 말씀드리면, 명세를 쓰고 끝낸 게 아니라 **서버를 실제로 띄워 27개 동작을 전부 호출하고 응답 53건을 명세와 대조했습니다.** 선언하지 않은 필드가 응답에 있으면 실패로 처리했고, 지금 불일치는 0입니다.

## 4:00 — 25쪽 고려사항과 다음 단계 〔마무리〕

마지막으로 고민한 점입니다.
가장 크게 고민한 건 **어디까지를 "확인된 것"으로 볼 것인가**였습니다.
별표26 57개 항목을 다 조사했지만 자동 채점으로 켠 항목은 **0개**입니다. 검증하지 않은 걸 공식 채점처럼 보여 주면 학습자에게 해가 되니까, 연습 표시와 안내만으로 나누고 화면마다 "공식 채점이 아니다"라고 적었습니다.
아직 확인 못 한 건 센서 핸들의 좌우 방향과 민감도 기본값이고, 실제 장비에서 측정해야 합니다.
다음 단계는 센서 실측으로 프리셋을 확정하고, 검증된 항목부터 자동 채점을 켜는 것입니다.
이상입니다. 감사합니다.
