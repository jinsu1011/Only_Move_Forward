# 프로젝트 보고서 작성 가이드

## 문서 용도와 역할

사용자가 직접 프로젝트 보고서를 작성할 때 참고할 구성·작성 방법이다. 보고서 본문이나 제출용 문장은 작성하지 않는다. Codex는 이 가이드와 설계·조사·검증 자료를 관리하고, 보고서 본문 및 제출용 PDF 작성은 별도 요청이 있을 때만 진행한다.

여기서 말하는 보고서는 과제 제출용 프로젝트 보고서다. 서비스 기능인 AI 개인 학습 보고서와 채팅의 단계별 진행 보고는 별개다.

## 작성 순서

1. 평가 체크리스트를 읽고 반드시 설명할 내용을 표시한다.
2. 대상·문제·서비스 목표를 먼저 정한 뒤 기능 범위를 연결한다.
3. UI 흐름에서 실제 사용자의 행동을 따라 설명 순서를 잡는다.
4. 같은 흐름의 데이터와 API를 연결해 설계의 일관성을 보여준다.
5. 공식 자료·센서·AI의 역할과 한계를 근거와 함께 정리한다.
6. 구현·검증 상태에 맞춰 표현을 조정하고 출처·부록을 붙인다.
7. 평가 기준과 대조하고 발표 시간에 맞춰 본문 분량을 줄인다.

## 화면 자료를 넣는 방법

- 전체 흐름도 다음에 대표 사용자 시나리오를 따라 화면을 배치한다.
- 화면마다 목적, 주요 입력, 주요 표시값, 버튼 동작, 다음 화면, 오류 복구를 짚는다.
- API 주석은 해당 버튼·데이터 옆에 배치하고 긴 명세 전체를 본문에 붙이지 않는다.
- 전체 화면 목록과 캡처를 대조해 빠진 화면이 없는지 확인한다.
- 보고서 작성 시점에 실제 화면이 완성되지 않았다면 ‘설계 와이어프레임’이라고 표시한다.

## 근거와 상태를 쓰는 방법

- 법령·시험 정보는 공식 원문을 다시 확인하고 출처, 시행일 또는 버전, 조회일을 적는다.
- 실제 수행한 검증에는 실행 방법과 반환 결과를 붙인다.
- 설계 제안, 구현 완료, 검증 완료를 별개로 표시한다.
- 미확인 사항은 한계·추가 확인 목록에 남긴다.
- 임의의 이용자 통계, 성능 수치, 효과, 공식 감점 값을 만들지 않는다.
- 예시 사용자 데이터는 예시라고 표시하고 실제 개인정보를 넣지 않는다.

## 발표에 맞추는 방법

발표 순서는 문제→서비스→사용 흐름→데이터/API→차별점·한계로 잡는다. 장별 시간 배분 초안은 `presentation-plan.md`를 참고하고 실제 리허설 후 조정한다. 세부 화면·표는 부록에 두되 필수 내용을 PDF 밖으로 빼지 않는다.

## 제출 전 확인할 것

- [ ] 평가 항목이 어느 장에서 충족되는지 rubric-checklist.md에 표시
- [ ] UI·ERD·API의 이름, 필드, 동작 대조
- [ ] 전체 UI 흐름과 화면을 PDF 내부에 포함
- [ ] 공식 자료 버전과 인용 위치 확인
- [ ] 실제 검증과 미완료 항목 구분
- [ ] 최상위 9반 평가 기준의 파일명·제출 방식·마감 재확인
- [ ] PDF·API YML·DBML 세 산출물의 최종 버전 일치
- [ ] PDF 가독성 및 발표 시간 확인
